# Agent Note: 用户发起的会话删除

Status: implemented

[English](2026-11-05-user-initiated-session-deletion.md) | 中文

## 问题

已存储的会话会在持久化根目录下不断累积，而 seam 没有删除单个会话的操作。已提交的代际本来不可变：[已发布格式迁移](2026-08-31-released-session-format-migrations.zh.md)从不移动、替换或删除它们，而[句柄模型](2026-08-27-handle-based-session-persistence.zh.md)保证每个会话只有一个写入方。因此，删除必须是用户明确发起的例外：它不能与写入方竞争，且不改变迁移行为。

## 决策

- `SessionPersistence.delete(id)` 是唯一移除已提交代际的操作，且仅在用户请求时执行。格式迁移从不移除、覆盖或移动已提交的代际。
- 删除要求写所有权：调用同时取得进程内认领与跨进程内核锁。若会话被任一实例或进程中的写句柄持有，或被本进程尚未实体化的已创建会话持有，则以 `SessionAlreadyOwnedError` 拒绝且不移除任何内容。未知 id 以 `SessionPersistenceNotFoundError` 拒绝。在移除开始前已中止的信号会使调用拒绝且不移除任何内容。
- JSONL 后端移除整个会话目录：全部代际、`session.lock` 以及会话自有文件。随后仅当项目目录为空时才移除它。
- 移除持久化完成后，后端以并行模式分发 `session/deleted`，载荷为 `{ sessionId }`。监听器丢弃其派生的逐会话状态。监听器失败会被记录日志，且不会使删除调用拒绝。
- 删除前已打开的读句柄不会保持可读：后端清除其已准备的历史前缀，因此之后的读取会抛出 `SessionPersistenceNotFoundError`。
- 附件存储有意不做清理。它在会话之间共享，因此逐会话删除无法安全地归属其条目。

## 考虑过的替代方案

**墓碑或软删除。** 它保留了用户要求移除的数据，并且仍需让代际保持可读或被重写，而迁移规则禁止这样做。

**基于时间或数量的保留策略。** 未经用户决定的自动清理会移除用户未选择的会话。`delete` 只移除一个指定的会话。

**不要求写所有权的删除。** 并发写入方可能在存在性检查与移除之间追加数据，留下部分或被重新创建的会话。所有权拒绝使移除相对于每个已知写入方保持独占。

**在移除之前发出事件。** 监听器会在会话仍然存在时丢弃派生状态，而移除失败时该状态已丢失。事件在移除持久化之后发出。

**随会话清理附件。** 附件在会话之间共享；逐会话清理可能删除其他会话仍在引用的数据。

## 后果

删除不可逆。目录移除之后、事件分发之前发生崩溃，会使监听器拥有的派生状态保持陈旧，直到该状态被重建；事件不会重放。第三方后端必须实现 `delete`，这是一项破坏性变更，记录于[升级指南](../../../../docs/upgrade-guide/v0.2.2-alpha.3/session-persistence-delete/guide.zh.md)。

## 测试

`packages/session/session-persistence-jsonl/tests/delete.spec.ts` 覆盖：从 `stat`、`open`、`list` 与磁盘中移除；有无同级会话时的项目目录清理；残留文件；未知 id；进程内写句柄；未实体化的创建方；外部内核锁；事件分发及其拒绝情形；监听器抛错；已中止的信号；删除后以同一 id 重新创建；以及当前会话与已迁移历史会话上的读句柄。
